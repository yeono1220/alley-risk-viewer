## ① 할 일 표 — 작성·링크 열

### 1. 3개 화면의 이동 흐름 정리
- 흐름: **F1 평가 요약 → (오류 건수 또는 요인 행 클릭) → F2 오류 목록(필터 적용된 상태) → (행 클릭) → F3 사례 상세 → "목록으로" 복귀 시 필터·run_id 유지, 이전/다음은 같은 필터 안에서 이동.**
- 화면 간에 들고 다니는 상태: `run_id`, `filters{error_types[], factor}`, `sample_id`. 이 3개만 있으면 어느 화면에서 새로고침해도 복원 가능.
- 10/30 와이어프레임을 클릭 가능한 프로토타입으로 연결했음: [프로토타입 링크]. 10/30 검토 시나리오(요약 → '미탐' 클릭 → S-002 열기 → 목록 복귀 → 다음 사례)가 끊김 없이 이어지는지 확인함.
- 화면 통합 대안 검토: 목록+상세 분할뷰(좌 목록·우 상세)는 PC에서 탐색이 빠르지만, 원본 이미지 확대 영역이 좁아져 "보행자·가림 영역을 충분히 볼 수 있다"는 완료 기준과 충돌. **첫 버전은 3화면 분리를 유지하고, 분할뷰는 bbox 협의 후 재검토**를 제안.

### 2. 정답·예측·근거·행동을 구분해 배치
- F3 배치: 상단 "비교 결과" 띠(판정 일치/불일치 + 오류 유형 뱃지) → 좌 원본 이미지(확대) · 우 검수 결과 → 하단 2열: **GT 열(녹색 상단선) | 예측 열(보라 상단선)**. 두 열은 같은 항목 순서(판정 → 요인 → 객체 → 근거 → 행동)로 정렬해 눈으로 바로 대조.
- 예측 열은 관측 사실 / 추론 / 권장 행동 / 판단 한계를 **분리된 행**으로 표시 (관측 불가 동작을 사실처럼 쓴 경우를 잡기 위함, S-011 사례).
- 빈 값 규칙: 근거 라벨 없음 → "미등록", confidence → "미정 (산출 방법 확정 전, 사고 확률 아님)", 미측정 지표 → "미측정"(0 아님), 보류 → 사유 + 부족한 정보 표시하고 안전/낮은 위험으로 바꾸지 않음.
- 대표 사례 12건(가상)을 넣었고 모든 화면에 "가상 데이터" 뱃지 표시. 핵심 가설 사례 S-003(판정은 맞으나 근거가 장소 상식뿐)이 "판정 일치 + 근거 오류"로 보이는지 확인함.

### 3. 백엔드에서 받을 정보 정리 (문혜승에게 먼저 공유)
- 첨부: `run.json`, `cases.json`, `taxonomy.json` — 세 파일이 그대로 API 응답 형태 제안.
- 필요한 엔드포인트(초안):
  - `GET /runs` → run_id, run_label, model_label, dataset_id, **data_kind(mock|real)**
  - `GET /runs/{run_id}/summary` → metrics, counts, error_counts, by_factor (run.json 구조)
  - `GET /runs/{run_id}/cases?error_type=&factor=&status=&page=&size=` → 목록 행(sample_id, thumbnail_url, gt.judgment, pred.judgment, error_types[], factors[], status)
  - `GET /runs/{run_id}/cases/{sample_id}` → image_url(고해상도), gt, pred, status, failure, review, error_types (cases.json 구조)
  - `POST /runs/{run_id}/cases/{sample_id}/review` → 검토 메모·오류 유형 저장
- 규약 요청: 미측정은 `null + status`로, 0으로 보내지 않기 / `error_types`는 배열(복수 허용) / `status`(ok, abstain, format_error, call_failed, label_review)와 모델의 `abstain_reason`을 분리 / confidence는 `null` 허용 / 이미지 접근 방식(서명 URL? 서버 프록시?)과 비식별화 여부.
- 정렬·페이지: 200장 이하면 페이지 없이 전체 조회로 충분 **[확인 필요: 최종 데이터 수]**. 정렬은 오류 유형 → sample_id 고정, confidence 정렬은 정의 후.

### 4. 예외 상태와 구현 순서
| 상태 | 화면 처리 |
|---|---|
| 로딩 | 요약 카드 자리에 스켈레톤. 숫자 자리에 0을 먼저 보여주지 않음 |
| 빈 결과(실행 없음) | "결과 파일 가져오기" 안내 + 버튼 |
| 조회 실패(API 오류) | 상태 코드·재시도 버튼. 캐시된 이전 결과를 몰래 보여주지 않음 |
| 이미지 로딩 실패 | 썸네일 자리에 "이미지 없음 (경로 확인)" 표시, 나머지 정보는 그대로 |
| 추론 실패/형식 오류 | 상세 상단에 코드·메시지·재시도 횟수, 원본 응답 접기. 예측 열은 "출력 없음" |
| 판단 보류 | 사유·부족 정보 표시. 판정 뱃지는 "판정 없음" |
| 라벨 재검토 | GT 열 "재검토 대기", 채점 제외 사유 표시 |
| 미실행 모델 | 실행 선택에 비활성 항목으로 표시, 비교 버튼 비활성 |
| 필터 결과 0건 | "조건에 맞는 사례 없음 + 필터 해제" |

- 프로토타입 상단의 "예외 상태 미리보기" 버튼으로 로딩/빈 결과/조회 실패를 바로 볼 수 있음.
- 기술 추천: **React + Vite + TypeScript**, 라우팅은 React Router(쿼리스트링에 run_id·filters 보존), 데이터는 TanStack Query. 이유: (1) 필터 상태를 URL에 두면 "필터 유지 복귀"와 링크 공유가 공짜 (2) mock JSON → 실제 API 교체가 fetch 함수 한 곳만 바꾸면 됨 (3) 팀 기존 후보 스택(React/FastAPI)과 일치. 스타일은 CSS 변수 + 최소 CSS, UI 라이브러리는 표·필터가 복잡해지면 그때 결정.
- 구현 순서와 예상 시간 (전제: 혼자, 하루 3~4시간 기준)
  1. 프로젝트 뼈대 + 타입 정의(run/cases/taxonomy JSON 기준) — 0.5일
  2. F1 요약 (mock) — 0.5일
  3. F2 목록 + 필터 + URL 상태 — 1일
  4. F3 상세 + 이전/다음 + 복귀 — 1일
  5. 예외 상태 9종 — 0.5일
  6. 실제 API 연결 + 이미지 접근 — 백엔드 완료 후 0.5~1일
  - 합계 약 4~5일. bbox 오버레이·모델 비교·검토 메모 저장은 협의 후 별도.

## 미정 사항 목록 (10/30 제출 형식의 마지막 항목)
1. confidence 표시 방식 — 숫자? 등급? 미정 상태로 둠
2. 위험 등급(low/medium/high) 경계와 안전/위험 변환 규칙
3. 허용 행동 집합과 행동 GT 기준 (행동 오류 판정에 필요)
4. bbox 포함 여부와 좌표 규약 → F3 오버레이 구현 여부
5. 보류·실패를 Recall 분모에 넣는 규칙 (현재는 보수적 집계 + 응답 사례만 둘 다 표시)
6. 라벨 재검토 사례 노출 범위 (목록에 보일지, 별도 탭일지)
7. 원본 이미지 외부 전송·발표 자료 사용 가능 여부
8. 웹에서 추론 실행 버튼 포함 여부 (현재 범위 밖)
